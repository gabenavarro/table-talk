# Landscape: Svelte-native GUI for table-talk

## 1. Svelte 5 today, and the custom-renderer PR

- Svelte 5 GA'd 2024-10-19; current is 5.45.0 (Dec 2025) with runes (`$state`, `$derived`, `$effect`, `$props`, `$inspect`) as the standing reactivity model, Svelte-4 syntax still supported. — https://sveltekit.io/blog/svelte-5 , https://www.scalablepath.com/javascript/svelte-5-review
- The custom-renderer API gpuix-svelte depends on is **sveltejs/svelte#18511**, and it is **open, unmerged**, still being force-pushed, with no changeset (no version targeted yet). It adds a `custom-renderer` export condition; without it, `mount()` isn't even exported (you get the server build). Reviewers have flagged the required path as untested. — https://github.com/sveltejs/svelte/pull/18511
- Consequence for gpuix-svelte: it can't depend on published Svelte at all. It **vendors a private build** — `vendor/svelte-5.57.0-ff9658a.tgz` in the repo I have locally, installed at `node_modules/gpuix-svelte/node_modules/svelte`, with every `svelte` import forcibly resolved to that copy via loader hooks (`--conditions custom-renderer --import tsx --import gpuix-svelte/register`). The README says explicitly: "**Do not add `svelte` to your own dependencies**: the registry's `svelte` has the same version number and none of the API." Confirmed by reading `gpuix-svelte/package.json` and `README.md` directly in the clone at commit b474c83.
- Background on the underlying need: Svelte 4 had a "foreign namespace" for Svelte Native, removed for the Svelte 5 compiler rewrite; a custom-renderer API (à la React DOM / React Native / Ink) has been requested since 2020 (#5496, #15470) and there's a dedicated community initiative. — https://github.com/sveltejs/svelte/issues/15470 , https://github.com/sveltejs/svelte/issues/5496 , https://svelte-custom-renderers.com/
- **What breaks if it never ships**: gpuix-svelte stays permanently pinned to a private fork of Svelte that the project must keep patching by hand against upstream compiler changes forever, ordinary Svelte tooling (SvelteKit, official Svelte VS Code/language-server assumptions, the wider plugin ecosystem) can silently diverge from the vendored build, and table-talk's Svelte components could never be shared verbatim with a normal Svelte web app without the export-condition dance. This is the single biggest risk in the whole approach — it rests on an unmerged, unreleased upstream PR maintained by a third party who isn't the Svelte core team's committed roadmap item.

## 2. GPUI (gpui.rs) status

- GPUI is Zed's own crate, "a hybrid immediate and retained mode, GPU-accelerated UI framework for Rust," explicitly **pre-1.0**: "There will often be breaking changes between versions." — https://github.com/zed-industries/zed/blob/main/crates/gpui/README.md
- Linux/FreeBSD: supports Wayland and/or X11 backends; both currently render via **Blade → Vulkan**. — same README; https://github.com/zed-industries/zed/tree/main/crates/gpui
- **In-flight architecture change**: an active PR removes Blade entirely and reimplements the Linux renderer on **wgpu** ("the blade graphics library is a mess and causes several issues for both Zed users as well as other 3rd-party apps using GPUI") — i.e., the Linux graphics backend table-talk would build on is mid-rewrite upstream, not settled. — https://github.com/zed-industries/zed/pull/46758
- Known Linux issues in the wild: `NoSupportedDeviceFound` when Vulkan can't find a compatible GPU, and Wayland+NVIDIA surface-acquisition / GPU-detection failures. — https://github.com/zed-industries/zed/discussions/28265 , https://github.com/zed-industries/zed/discussions/33802
- Fonts/emoji on Linux (via `cosmic-text`, GPUI's Linux text stack): **COLRv1 color emoji renders blank** — cosmic-text doesn't yet support the COLRv1 table Fedora's `Noto-COLRv1.ttf` ships, and it also mis-selects the monochrome Noto Emoji over color Noto Color Emoji, ignoring fontconfig fallback rules. There are also separate GPUI font-size regressions specific to Wayland. Workaround exists (swap in upstream `NotoColorEmoji.ttf` with CBDT bitmap tables) but it's a system-font substitution, not something the app controls. — https://github.com/zed-industries/zed/issues/51171 , https://github.com/pop-os/cosmic-text/issues/310 , https://github.com/zed-industries/zed/issues/30526
- IME/HiDPI: GPUI's Linux input path targets `zwp_text_input_v3` (Wayland IME protocol) and HiDPI via `wp_viewporter`; both are Wayland protocols with **no X11 fallback** described for IME. Font stack is FreeType/HarfBuzz/Fontconfig-based, standard for Linux apps. (Search-summarized; I could not independently confirm this against GPUI source in the time budget — treat as directionally right, not vendor-verified.)
- **@gpuix/native** (the actual npm addon gpuix-svelte rides on) is a separate, third-party project (`remorses/gpuix`, Apache-2.0), *not* published by Zed/GPUI itself: "Node.js & React bindings for Zed's GPUI... no Electron," napi-rs bindings with prebuilt per-platform binaries for darwin-arm64, darwin-x64, linux-x64-gnu, linux-arm64-gnu (Windows too, per gpuix.dev). — https://github.com/remorses/gpuix , https://gpuix.dev/
- gpuix-svelte pins `"@gpuix/native": ">=0.7.0 <=0.8.0"` (read from its `package.json`). Changelog shows rapid churn to version 0.7 (0.2→0.7 in the visible history) with Linux-specific caveats still open at 0.7.0: **"Linux currently ignores `focus` and `show` because GPUI does not support those flags there,"** and Linux builds lack a headless test renderer (GPU test support exists elsewhere, not on Linux). — https://github.com/remorses/gpuix/blob/main/CHANGELOG.md
- Standalone-binary size (Bun-compiled): **~80 MB** — Bun runtime + Svelte runtime + a 17 MB GPUI native addon — built per-host-platform, no cross-compiling. Browser/WASM build of the same components is a 19.9 MB uncompressed download requiring COOP/COEP cross-origin isolation headers and Bun's bundler (Node can't build it). — README.md in the local clone.
- Net: GPUI is real, GPU-accelerated, and native, but it is (a) pre-1.0 with routine breaking changes, (b) mid-rewrite on the exact Linux graphics backend in question, (c) has open, currently-unresolved emoji/font correctness bugs on Linux, and (d) is bridged to Node/Svelte only through a third-party binding (`@gpuix/native`) that is itself young (sub-1.0, fast-churning) and imposes its own Linux feature gaps (window focus/show).

## 3. Alternatives compared

| Approach | Native feel | Risk | Effort | Linux/macOS | Distribution | Python coupling | Reversibility |
|---|---|---|---|---|---|---|---|
| **gpuix-svelte (GPUI)** | Real native window, GPU-drawn, no webview | High — rides an unmerged Svelte PR (private vendored fork) + pre-1.0 GPUI + pre-1.0 3rd-party binding; Linux emoji/font bugs open; Linux graphics backend mid-rewrite upstream | High — no CSS engine, must reimplement styling to GPUI's flexbox subset, no `bind:`, roll your own scrollbars/context menus/mermaid rendering | Both listed as supported; Linux is the least-exercised path (test renderer has no headless GPU on Linux) | ~80 MB self-contained binary per platform (Bun compile), or `npm install` + run via Node/Bun; no cross-compile | None built in — Python stays external, must be shelled out to or spoken to over a socket/HTTP from Node | High friction to unwind (whole UI layer is GPUI-shaped; components aren't portable to DOM without the custom-renderer condition) |
| **Tauri 2 + Svelte (webview + Rust shell)** | Native window chrome, OS webview content (not "raw DOM feel" but standard desktop webview apps) | Low-medium — Tauri 2 is stable, widely used, webview quirks (WebKitGTK on Linux) are the main gotcha | Medium — normal SvelteKit/Svelte app, Rust shell mostly boilerplate, sidecar wiring for Python is a documented pattern | Both well supported; official docs and examples for Python sidecars on both | ~5–10 MB installer typical (20–50x smaller than Electron); bundles a Python sidecar binary per-platform (e.g. `python-x86_64-unknown-linux-gnu`, `python-aarch64-apple-darwin`) | Clean: Python runs as a bundled sidecar process, Rust/JS talk to it over stdio or local HTTP | High — swap the webview frontend independently of the Python backend; NiceGUI dashboard keeps running in parallel with zero interference |
| **Electron** | Native window, Chromium content | Low technically, ruled out on footprint | Low (huge ecosystem) | Both | 120–200 MB bundle, ~150–400 MB idle RAM vs Tauri's ~40–80 MB | Same sidecar pattern as Tauri, just heavier host | High, but not worth building — no capability Tauri lacks here, only cost |
| **Svelte 5 SPA + Python stdlib `http.server` + SSE** | Feels like a local web app (opens the OS default browser, or an app-mode window flag) — not a native window | Low — everything is stdlib Python + a static Svelte build, no Rust/Node/Bun toolchain to keep alive at runtime | Low-medium — build the Svelte bundle once, commit the static output, serve with `http.server` + a hand-rolled SSE endpoint over the existing JSONL-folding `tt_model` | Both trivially (pure Python + a browser, no native deps) | Zero extra binary — ships as part of the existing `bin/table-talk` Python package; static assets committed | Tightest possible — Python IS the app, JS is presentation only, SSE straight from the same fold logic the NiceGUI dashboard already uses | Highest — can run side-by-side with NiceGUI dashboard trivially, delete either without touching the other |
| **Bun/Node single-binary** | Whatever UI toolkit runs inside it (still needs a renderer choice — DOM via webview, or GPUI, or terminal) | Depends entirely on the renderer picked; the "single binary" part just changes packaging | Low packaging effort, but `bun build --compile` alone produces a **57 MB "hello world"** before any UI code — this is a distribution mechanism, not a UI answer | Both, but no cross-compiling (built per host) | 50–80+ MB baseline per platform | Needs a Python bridge same as above options | Medium — orthogonal axis, doesn't itself decide the rendering story |

Sources for this table: Tauri sidecar bundling — https://tauri.app (per search summary) and https://github.com/dieharders/example-tauri-v2-python-server-sidecar ; Tauri bundle-size claims — https://rustify.rs/articles/rust-tauri-v2-desktop-app-tutorial-2026 ; Tauri vs Electron memory/startup — https://www.gethopp.app/blog/tauri-vs-electron , https://tech-insider.org/tauri-vs-electron-2026/ ; Bun compiled-binary size — https://bun.com/docs/bundler/executables.md ; gpuix-svelte size/build facts — local clone `README.md` at commit b474c83.

## 4. Can the same Svelte components run on both DOM and GPUI?

Realistic only within tight limits, per gpuix-svelte's own README (read directly from the clone):
- No CSS engine: only inline styles / `<style>` blocks compiling to flexbox-plus-basics reach GPUI (spacing, position, color, typography, hover/active, CSS vars via `set_css_vars()`); **units beyond px, shorthand CSS, transforms, transitions, and most selectors are dropped**.
- No `bind:` directive — input state must flow through explicit events, unlike idiomatic DOM Svelte.
- No native scrollbars, no OS context menu on right-click, SVG doesn't inherit color.
- Component code that avoids all of the above (plain flex layout, px units, explicit event handlers, no `bind:`) is the realistic shared subset — gpuix-svelte demonstrates exactly this by running its own demos unmodified on GPUI **and** on GPUI's own WebAssembly/WebGPU canvas build (not the DOM — a `<canvas>`, so still not "real DOM Svelte"). There is no demonstrated case of one component tree running on GPUI *and* on an actual DOM renderer; the "browser" story here is GPUI-via-WASM-canvas, not DOM.
- Practically: writing table-talk's UI to that shared subset means giving up most CSS you'd otherwise reach for, and still not getting genuine DOM portability — only GPUI-native and GPUI-in-a-canvas.

## 5. Mermaid in a non-DOM renderer

Mermaid's real layout engine needs actual browser geometry APIs — attempts to fake this with jsdom/canvas polyfills "either fail outright or produce broken output." — https://blogo.timok.deno.net/posts/mermaid-ssr-renderer (via search) , https://github.com/mermaid-js/mermaid/issues/3886
Options, in order of how proven they are:
1. **mermaid-cli (`mmdc`) via Puppeteer** — the official, "only reliable" server-side path; spins a headless Chromium per invocation (slow, but correct, and it's what most CI/doc pipelines actually use).
2. **Pure reimplementations, no browser**: `sebastianjs` (Node/TS), `go-mermaid` (Go), `mermaidx` (Python, embeds QuickJS + resvg, "no Node.js, no npm, no Chrome"), `rendermaid` (TS, AST→SVG). All are third-party, much less battle-tested than official mermaid, and coverage of Mermaid's full syntax is unverified. — https://github.com/MohammadRaziei/mermaidx , https://github.com/zkrebbekx/go-mermaid , https://github.com/creadri/sebastianjs
3. **Rasterize an SVG** (from option 1 or 2) to a bitmap and draw that as an image inside GPUI — the only path that fits a non-DOM renderer with no SVG engine of its own; GPUI does render raster images and gpuix-svelte notes "SVG inherits no color natively," implying at least basic SVG display exists but is limited.
4. **Fall back to text** (render the Mermaid *source*, monospaced, or a pre-rendered PNG committed at generation time) — the ponytail-simplest option, and viable since table-talk's diagrams are logged once and read many times, not edited live in the GUI.
For table-talk specifically: since mermaid diagrams are recorded events (not user-edited live), rendering them once server-side (Python subprocess to `mmdc`, or `mermaidx` if a pure-Python path is preferred to avoid a Node/Chromium dependency) to a PNG/SVG file, then displaying that as a static image, sidesteps needing any in-renderer Mermaid engine at all — this works identically whether the eventual GUI is GPUI, Tauri/webview, or the SSE+browser SPA.

## 6. File watching (Linux/macOS, Node)

- `fs.watch` (Node built-in): platform behavior differs a lot; historically no recursive support on Linux, **added in Node.js via PR #45098 (landed 2022)** — Linux/AIX/IBMi previously threw `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM` for `recursive: true`. Even non-recursive, `fs.watch` has known quirks: double-fires, "rename"-only events, no filename on some platforms/editors. — https://github.com/nodejs/node/pull/45098 , https://github.com/nodejs/node/issues/36005
- **chokidar**: the ecosystem default, `fs.watch`-based (no polling, so lower CPU), well-normalized cross-platform API, but "slow" on large trees and known to hit file-descriptor limits on big projects.
- **@parcel/watcher**: native C++ Node addon, "much faster out of the box," supports a Watchman backend, "faster than chokidar on large trees, no daemon required," used by Tailwind/Nx/Nuxt/VS Code. Recommended once a tree exceeds ~50k files or chokidar's CPU/memory becomes a problem. — https://www.npmjs.com/package/@parcel/watcher , https://github.com/11ty/buildawesome/discussions/4025
- For table-talk: the JSONL log directory is small (per-day, per-project files) and append-only, so plain `fs.watch` (or even a 1–2 s poll of file size/mtime, matching the existing NiceGUI dashboard's own "fold every 2 s" cadence) is almost certainly sufficient — chokidar/`@parcel/watcher` would be reaching for large-scale-repo tooling to solve a "watch a handful of log files" problem.

## 7. Prior art: terminal/tmux-styled dashboards in Svelte or GPUI

- **Webmux** (Windmill) — a Svelte 5 dashboard for orchestrating parallel AI coding agents, using **xterm.js** for terminal rendering in the DOM, with a backend driving git/tmux/Docker/GitHub CLI — i.e., DOM Svelte + a terminal-emulator widget, not a native-GPU renderer. Closest existing analog to "a wall of session windows" built in Svelte. — https://www.windmill.dev/blog/webmux
- **SvelTUI** (`RLabs-Inc/sveltui`) — brings Svelte 5's reactive model to an actual terminal UI (TUI), not GPUI and not the DOM — a third rendering target entirely (curses-like). Shows appetite for "Svelte, but not the DOM" beyond just GPUI. — https://github.com/RLabs-Inc/sveltui
- **svelte-nodegui** — native cross-platform desktop apps via Node.js + Qt5, CSS-like styling, a different native-widget approach (Qt, not GPU-drawn) predating GPUI-based options. — https://github.com/nodegui/svelte-nodegui
- No prior art found of a tmux-style *native GPUI* dashboard in Svelte — gpuix-svelte's own demo set (counter, tic-tac-toe, HN reader, liquid-glass control panel) is the closest thing, and none of them are multi-pane/session-wall UIs.

## What this means for table-talk (10 lines)

1. gpuix-svelte is a genuinely elegant demo, but it sits on two unreleased foundations at once: Svelte's unmerged custom-renderer PR (#18511, vendored as a private fork) and GPUI itself (pre-1.0, Linux graphics backend mid-rewrite from Blade to wgpu, open COLRv1 emoji rendering bugs on Linux). Betting the dashboard on it means betting on two upstream projects table-talk doesn't control shipping stable releases.
2. `@gpuix/native`, the actual npm bridge, is third-party (not Zed), sub-1.0, and already documents Linux-specific gaps (window focus/show ignored) — a second layer of "not quite there yet" on the platform NON-NEGOTIABLES explicitly require (Linux and macOS both work).
3. There is no CSS engine and no `bind:` in GPUI-Svelte — every dashboard feature (rows, columns, filters, forms) needs re-implementation against a much smaller styling vocabulary, which is real, ongoing effort, not a port.
4. Mermaid has no non-DOM rendering story of its own; the workable answer (pre-render to SVG/PNG server-side, display as an image) is renderer-agnostic — it costs the same whether the eventual GUI is GPUI, Tauri, or a browser SPA, so it's not a reason to prefer GPUI.
5. Tauri 2 + Svelte is boring, proven, and satisfies every NON-NEGOTIABLE today: stable release, Linux+macOS both first-class, Python stays untouched behind a sidecar process, ~5–10 MB installer, and it's trivially reversible (swap frontends without touching `bin/table-talk` or the JSONL format).
6. The Python-stdlib-`http.server`-plus-SSE option is the laziest thing that could work: no Node/Bun/Rust toolchain at runtime at all, Python (`tt_model`) stays the single source of truth, and it can run *next to* the existing NiceGUI dashboard with zero interference — the strongest reversibility of any option.
7. File watching is a non-problem either way — table-talk's JSONL directory is small; `fs.watch` or a dumb poll matching the dashboard's existing 2 s fold cadence beats reaching for chokidar/@parcel/watcher.
8. No prior art exists for a tmux-style session wall built natively in GPUI; Webmux (Svelte + xterm.js, DOM) is the closest analog to "a wall of windows," and it's a DOM app.
9. Ponytail reading: GPUI is the most machinery and the most unresolved risk for the least proven payoff right now; it is worth prototyping in parallel (cheap, since gpuix-svelte needs no toolchain beyond `npm install`) but not worth committing the primary path to while #18511 is unmerged and GPUI's Linux backend is being rewritten under it.
10. Recommended default direction pending a design conversation: Tauri 2 + Svelte 5 for real native-window feel with proven Linux/macOS support and a Python sidecar for `tt_model`, with the SSE+stdlib-server option kept as the fallback/reversibility anchor; revisit GPUI once #18511 merges and ships in a released Svelte and GPUI's Linux wgpu rewrite lands.
